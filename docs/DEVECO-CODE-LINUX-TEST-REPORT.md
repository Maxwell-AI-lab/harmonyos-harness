# DevEco Code Linux 版功能测试报告

*基于 harness-dev:2.1 自行构建的 Linux 版 DevEco Code 1.17.9 · 镜像 harness-dev:2.2 · 2026-11-23 · bms173*

## 一、结论

> **DevEco Code 的鸿蒙开发能力在 Linux 上可以正常工作，并且适合无人值守批量运行**。在全新容器里不做任何手动步骤，agent 自己完成“构建 → 安装 → 启动 → 界面验证 → 截图”全流程；未登录华为账号，模型走自有网关。

| 1.17.9 | 22.3GB | 18/19 | 30 秒 | 0 次 |
| --- | --- | --- | --- | --- |
| DevEco Code 版本（源码构建） | 镜像 harness-dev:2.2（2.1 + 1.4GB） | 官方实机用例可运行项通过数 | 新容器首次启动模拟器 | 批量运行需要的人工确认 |

有三件事决定了“能不能用”，是只做冒烟测试（`--version` / `--help` / `serve`）发现不了的：

| # | 事实 | 说明 |
| --- | --- | --- |
| 1 | **鸿蒙工具不在二进制里** | 由内建插件 `@deveco-test/deveco-harness` 提供，它是平台包 package.json 里的普通 npm 依赖，装在二进制旁边的 `node_modules`。缺了它，`deveco` 照常启动，但技能只有 2 个、鸿蒙工具一个都没有 |
| 2 | **Linux 走“命令行工具”模式** | 内置的 deveco-cli 在 Linux 上明确拒绝 DevEco Studio 模式，用 `DEVECO_CLI_CLT_PATH`（基础镜像已设）；`DEVECO_HOME` 只管宿主层的技能解锁与 hdc 守卫，镜像里用软链接做了适配目录 |
| 3 | **`build_project` / `start_app` 已不是工具** | 1.17.9 把它们移除了（上游单测断言它们不存在），能力改为 agent 通过 bash 调 `devecocli`。现存内建鸿蒙工具：`verify_ui` / `get_ui_verification_log` / `save_ui_screenshot` |

## 四、SDK / API 版本

| 组件 | 版本 | 说明 |
| --- | --- | --- |
| 命令行工具（CLT） | 26.0.0.821 | 镜像里这套来自社区镜像仓，是该仓的最新版（2026-09-02）。官方下载中心需登录，是否有 26.0.1 的 Linux 包未确认 |
| CLT 自带的 SDK | API 26 | `HarmonyOS SDK: HarmonyOS 26.0.0 Release` |
| 模拟器系统镜像 | API 24 | HarmonyOS 6.1.1(24) |

> **批量跑时真正要注意的 SDK 版本问题**：SDK 是 API 26，模拟器是 API 24。不指定 API 级别新建的工程默认 API 26，**能构建成功，但装不上模拟器**。实测：
>
> `error: failed to install bundle. code:9568297 error: install failed due to older sdk version in the device.`
>
> 解决：新建工程时指定 `--api-level 24`；已有工程把 `build-profile.json5` 里的 `targetSdkVersion` / `compatibleSdkVersion` 设为 `"6.1.1(24)"`。

> **这个不一致没法消除，但 agent 能自己处理**。命令行工具默认取 SDK 里的最高 API 级别（`detectApiLevel()` 直接返回最大值），没有可配置的开关；官方远端镜像目录里最新的模拟器系统就是 HarmonyOS 6.1.1（API 24），没有 API 26 的镜像。<br> 实测不给任何提示，让 agent 自己新建工程并安装到模拟器（当时模拟器还没启动）：它自己启动了模拟器，发现“模板默认 API 26，而模拟器为 6.1.1(24)”，把 `build-profile.json5` 改成 `6.1.1(24)` 后安装运行成功，全程 2 分 13 秒，并如实报告了自己改了什么。<br> 所以只有**不经 agent、直接用脚本调 `devecocli create` 和 `run`** 的流程会真的失败，那种情况必须自己加 `--api-level 24`。

> **反过来的问题：用了 API 26 才有的接口，构建时发现不了，运行时才崩**。工具链是 API 26，模拟器是 API 24。在一个按 `--api-level 24` 新建的工程里调用 `fs.listFileExtSync`（`@ohos.file.fs` 里 API 26 才有的函数），实测：<br> 命令行构建成功，只给一条“函数可能抛异常”的通用提醒；ArkTS 检查同样只有这条通用提醒；Lint 报 0 问题（Lint 确实在运行，埋一个未使用的变量能被报出来）。也就是说**构建阶段没有任何一步比对接口的版本**。<br> 装到模拟器上（系统 6.1.0.126，API 24）直接调用：应用一启动就崩，崩溃报告是 `TypeError: listFileExtSync is not callable`，位置就是调用那一行。用 try/catch 包住则能接住，应用照常运行。<br> 对现有迁移结果的影响：没有发现。只读扫描了同事流水线的 155 个任务，其中 87 个有完整工程（全部声明的是 `6.1.1(24)`），共 6795 个源文件，对照 SDK 里 API 26 新增的接口（704 个模块级名字、38 个全新模块、1214 个只在 API 26 出现的方法 / 属性名），按每个文件的 import 关系比对，结果是 0 处。这个扫描器在探针工程上能扫出埋下的调用，在干净的模板工程上是 0。<br> 这个风险没法靠换版本消除（没有 API 26 的模拟器系统镜像），只能加防护：把扫描加成流水线里的一步，或者给 agent 写一条“只用 API 24 及以前的接口”的规则。这两样都还没做。

**`check compat` 不可用** 是另一件较小的事：该功能要求命令行工具 ≥ 26.0.1，只影响这一个命令。升级命令行工具会同时换掉 SDK 和模拟器程序，可能影响与现有 API 24 系统镜像的兼容性，以及同事流水线已验证过的构建行为，所以没有动。

## 五、镜像里做的非默认设置

| 项 | 内容 | 原因 |
| --- | --- | --- |
| 编译期开关 `--skip-agreement` | 产品协议的硬性检查直接放行 | 上游构建脚本自带的开关，注释写明用于源码/内部构建，发布版固定关闭。本镜像仅内部使用，所以开启（用户确认）。实测删掉协议接受文件后 agent 对话照常进行 |
| 协议接受 | 模拟器许可；另保留产品协议的接受记录 | 许可必须接受。产品协议的硬性检查已被上面的开关绕过，保留接受记录只是因为交互式界面的引导流程只看本地记录、不看那个开关 |
| 隐私 | 关闭数据统计、工具改进计划、CLI 遥测、自动更新检查 | 默认都开启；服务器上批量跑不向华为上报使用数据 |
| 窗口模式 | 入口脚本自动拉起 Xvfb :0，`DISPLAY=:0` | 无窗口模式模拟器无法注册到 hdc；截图对比和 VNC 也要窗口模式 |
| 预置模拟器实例 | `deveco_phone`，已完成首次启动（0.76GB） | 新容器首次启动 30 秒，而不是 85 秒加一条超时提示 |
| Lint 默认生效 | 给 `devecocli create` 的配置模板加一条规则（`enable-lint.py`） | 上游的默认配置会被检查器跳过，新建工程的 Lint 什么都不查却显示“无问题”。见第十一节 |
| 冒烟等待 | `DEVECO_CLI_SMOKE_WAIT_MS=10000`（默认 3000） | 冷启动时应用首次启动可能超过 3 秒，会被 `devecocli run` 误判为 FAIL_CRASH |
| 系统镜像软链接 | `/root/Library/Huawei/Sdk/system-image` | CLI 启动模拟器不带 `-imageRoot`，默认到这个位置找镜像 |

镜像设置了 `ENTRYPOINT`（先启动虚拟显示器再执行原命令），不想要时用 `docker run --entrypoint bash ...`。

## 六、仍然存在的问题

| 级 | 问题 | 说明 |
| --- | --- | --- |
| ❌ 高 | SDK API 26 与模拟器 API 24 不一致 | 见第四节。批量建工程必须指定 API 24 |
| ⚠️ 中 | 调用了 API 26 才有的接口时，构建不报错、运行时才崩 | 见第四节。扫描 87 个迁移工程没有发现；目前没有任何防护，可加扫描步骤或给 agent 加规则 |
| ❌ 高 | 宿主机 inotify 监听限额 | 所有容器共用 root 的额度，老内核默认 8192 个 watch，并发构建时报 `ENOSPC: System limit for number of file watchers reached`。bms173 已调到 1048576 并持久化；换机器要重设 |
| ⚠️ 中 | `verify_ui` 依赖能看图的模型 | 默认指向华为内置的多模态模型（需登录）。用自有网关时要在配置里给 `ui_verification` 指定，且模型名必须是网关在 OpenAI 兼容路由上认识的 |
| ⚠️ 中 | 模型网关的两个问题 | 并发流式请求结算时 `SQLITE_BUSY`；模型名映射只在 Anthropic 协议路由上生效。这两点是同事的 new-api 网关的问题，会影响所有客户端 |
| ⚠️ 中 | 多个模拟器实例时需指定设备 | `devecocli run` 报 `DEVICE_SELECTION_REQUIRED`，要加 `--device` |
| ⚪ 低 | Lint 在上游默认配置下不检查（镜像里已处理） | 镜像里新建的工程已默认生效；已有的工程如果配置仍是上游默认内容，需要自己改动一条规则或用 `--config-path`。见第十一节 |
| ⚪ 低 | 没有 ArkTS 的语言服务（DevEco Code 的语言服务默认关闭，打开后也只覆盖 .ts / .js）；命令沙箱不生效 | 见第十一节 |
| ⚪ 低 | `check compat` 不可用 | 需命令行工具 ≥ 26.0.1 |
| ⚪ 低 | 官方用例 4 个失败 + 1 个 | 4 个是测试代码只适配 Windows；ATTACH 在无终端容器里未通过 |

## 八、需要如实说明的几件事

- **遥测上传过一次**：在我发现遥测开关之前，最早的测试容器里手动测试时，CLI 至少成功向华为上传过一次遥测数据（上传状态里有时间戳）。这是它默认开启的行为；最终镜像里已关闭。
- **改了宿主机的一项系统参数**：bms173 的 `fs.inotify.max_user_watches` 从 8192 调到 1048576，`max_user_instances` 从 1024 调到 8192，写在 `/etc/sysctl.d/90-inotify-limits.conf`。放宽上限不预占内存。同事的流水线容器同样受益。
- **镜像大了 1.4GB**：运行时依赖约 0.6GB，预置模拟器实例约 0.76GB。后者是可选的，删 Dockerfile 里一行即可去掉。
- **用到了同事 rsi 网关的凭证**：用于配置模型供应商并发起测试对话，测试完成后已从容器和临时目录中删除。服务器上没有残留。
- **服务器上的 `harness-dev:2.1-deveco` 不是我打的**：装的是 `0.0.0-develop-202611230929`，没有运行时依赖，技能数 2，鸿蒙工具没有加载。

## 九、自检结果（2026-11-24，最终镜像）

## 十一、几项“不可用 / 不检查”的具体含义

这几项之前只有一句结论，这一节说明它们各是什么、在 Linux 上实际的表现、对使用有什么影响，以及依据。前三项不影响已经验证通过的构建、运行、模拟器、界面验证等核心流程。（2026-11-24 更正：“语言服务”一项原先写的是“不可用”且原因标了“未确认”，读源码并实测后已改正，见下表。）

| 功能 | 它是什么 | 在这个镜像里的实际表现 | 影响与依据 |
| --- | --- | --- | --- |
| **语言服务** | 编辑器背后的代码理解能力：不构建就报出编译错误、按名字搜符号、看文件里有哪些函数、代码格式化 | **是 DevEco Code 自带的功能，不是要对接的外部服务**（不用配地址、令牌），但默认关闭。启动日志写着 `all LSPs are disabled` 和 `all formatters are disabled`。在 `deveco.json` 里写 `"lsp": true` 后，日志变成 `enabled LSP servers …`：给一个引用了未定义变量的 `.ts` 文件要诊断，能即时报出 `Cannot find name 'undefinedVariable'`；给同样有错误的 `.ets` 文件要诊断，仍返回空的 `{}` | **影响**：对鸿蒙工程没有变化——ArkTS 代码没有即时的诊断和格式化，agent 要知道代码有没有编译错误只能靠构建和 `devecocli check arkts`。实测 agent 就是这么做的（每次都先构建），所以不阻塞。<br>**它怎么工作**：DevEco Code 自带“提问”的那一半；“回答”的那一半是每种语言一个的程序，第一次用到时 DevEco Code 自己从 npm 下载到缓存目录（实测约 9MB），可以用 `DEVECO_DISABLE_LSP_DOWNLOAD` 关掉下载，也可以在配置里指定自己装的。<br>**依据**：源码 `lsp/lsp.ts` 里，只有配置的 `lsp` 一项为空或 false 时才打印 all LSPs are disabled；配置项的说明是“不写或设为 false 即关闭，true 启用内置的，或写成对象启用内置的并加覆盖”。所以各个平台默认都是关闭，不是 Linux 特有的。内置的 38 种语言服务器（`v1/config/lsp.ts` 的 `builtinServerIds`）里没有 ArkTS；内置命令行工具里 `assertLsp()` 直接转给 `assertStudio()`，即 ArkTS 的语言服务随 DevEco Studio 提供，Studio 没有 Linux 版，所以这部分在 Linux 上补不上。<br>**打开时的一个坑**：工程里的 `typescript` 包要是 5.x。直接 `npm install typescript` 现在装到的 7.0.2 里没有它要找的 `lib/tsserver.js`。<br>**未确认**：官方安装包会不会自带一份打开语言服务的配置（没有官方的 Linux 安装包，无法对比） |
| **命令沙箱** | 限制 agent 执行的命令能做什么：`read-only`（只读）、`workspace-write`（只能写工作区）、`full-access`（不限）三档，由系统层强制执行 | 不生效。所有命令都是直接执行，相当于永远是 `full-access` | **影响**：如果想靠“只读”或“只能写工作区”来约束 agent，在这套镜像上不起作用，剩下的约束只有工具层的权限审批和容器本身的边界。用 `--auto` 无人值守时等于没有这层约束，所以容器就是唯一的安全边界。<br>**依据**：源码 `tool/shell.ts` 里 `isSandboxPlatform = isMac \|\| isWindows`；依赖的 `@bitfun-ai/sandbox` 0.3.1 在 npm 上只有 Windows 和 macOS 平台包 |
| **`check compat`** | SDK 兼容性扫描：检查源码用了哪些在目标 SDK 版本里变更或废弃的接口，需要指定源版本和目标版本，可导出报告 | 报错 `The apicompat component is missing. The detected Command Line Tools version is 26.0.0.821. The minimum required version is 26.0.1` | **影响**：只影响这一个命令。agent 做跨 SDK 版本升级时没有这个辅助工具。<br>**依据**：实测报错原文 |
| **`check lint`** | 代码规范检查：按 `code-linter.json5` 里的规则查问题，模板默认启用了性能规则、TypeScript 推荐规则和一组安全规则 | **镜像里新建的工程默认生效**。上游原版在这里什么都不检查：结果是“检查了 0 个文件、无问题” | **上游的问题**：新建工程自带的配置与检查器内置的默认配置完全相同，命令行模式下检查器遇到默认配置会跳过执行规则的引擎，连模板里写成 `error` 的安全规则也不执行，等于给了一个假的“全部通过”。<br>**依据**：检查器日志 `Using default configuration, skipping ESLint engine`（整个过程 0.05 秒）。对照实验：默认内容 + 默认文件名 → 跳过；默认内容 + 其他文件名 → 跳过；非默认内容 → 报出了未使用变量。所以是按**内容**判定是否为默认配置<br>**镜像里的处理**：`enable-lint.py` 给 `devecocli create` 的配置模板加一条 `@typescript-eslint/no-unused-vars`（本来就在推荐规则集里，显式写出只为让配置不等于默认）。参数设成不检查未使用的函数参数，因为模板自己的 `EntryAbility.ets` 就有两个未使用的回调参数，否则每个新工程一建出来就带两个“错误”。实测：干净的模板工程 0 问题；埋入未使用的导入和局部变量后被报出；命令行直接用的 `devecocli` 和 DevEco Code 内置的那一份都生效<br>**仍然要注意**：只对镜像里新建的工程生效，已有工程若配置还是上游默认内容需要自己改；汇总里的 `Files checked` 统计的是有问题的文件数，引擎被跳过和检查过没问题都显示 0，不能据此判断 Lint 是否真的跑了；同一个文件里的 `any` 类型和 MD5 调用即使把对应规则设成 `error` 也没被报出，原因不明；这是否只在 Linux 命令行模式下如此没有确认 |

### 值得反馈给 DevEco Code 团队的

- 新建工程自带的 Lint 配置刚好触发“默认配置跳过”，默认情况下规则全部不执行。
- 模板生成的 `EntryAbility.ets` 违反模板自己的 Lint 规则。
- 鸿蒙能力不在二进制里：缺少运行时依赖时没有任何提示，只是静默地没有功能。
- 新模拟器实例首次启动的时间超过 CLI 的等待时间；冒烟检查的等待时间在冷启动下不够。
- 官方实机用例有 4 个只适配了 Windows。
- 命令行构建不比对接口版本：工程声明的兼容版本低于所用接口的版本时，构建、ArkTS 检查、Lint 都没有任何提示，运行时才崩。

### 服务器上另一个自己编译的版本（`harness-dev:2.1-deveco`）

那个镜像把压缩包解压后只装了二进制，有三个问题：agent 对话默认被产品协议拦住；内建鸿蒙插件没有加载（技能 2 个，界面验证工具、鸿蒙技能、hdc 守卫都没有）；模拟器相关的配置全部缺失。它能启动，agent 也能靠基础镜像里现成的 `hvigorw` 完成构建，但用不上 DevEco Code 自己的能力。建议换用 `harness-dev:2.2`。
