四、SDK / API 版本

组件版本说明
命令行工具（CLT）26.0.0.821镜像里这套来自社区镜像仓，是该仓的最新版（2026-09-02）。官方下载中心需登录，是否有 26.0.1 的 Linux 包未确认
CLT 自带的 SDKAPI 26HarmonyOS SDK: HarmonyOS 26.0.0 Release
模拟器系统镜像API 24HarmonyOS 6.1.1(24)
批量跑时真正要注意的 SDK 版本问题：SDK 是 API 26，模拟器是 API 24。不指定 API 级别新建的工程默认 API 26，能构建成功，但装不上模拟器。实测：
error: failed to install bundle. code:9568297 error: install failed due to older sdk version in the device.
解决：新建工程时指定 --api-level 24；已有工程把 build-profile.json5 里的 targetSdkVersion / compatibleSdkVersion 设为 "6.1.1(24)"。
这个不一致没法消除，但 agent 能自己处理。命令行工具默认取 SDK 里的最高 API 级别（detectApiLevel() 直接返回最大值），没有可配置的开关；官方远端镜像目录里最新的模拟器系统就是 HarmonyOS 6.1.1（API 24），没有 API 26 的镜像。
实测不给任何提示，让 agent 自己新建工程并安装到模拟器（当时模拟器还没启动）：它自己启动了模拟器，发现“模板默认 API 26，而模拟器为 6.1.1(24)”，把 build-profile.json5 改成 6.1.1(24) 后安装运行成功，全程 2 分 13 秒，并如实报告了自己改了什么。
所以只有不经 agent、直接用脚本调 devecocli create 和 run 的流程会真的失败，那种情况必须自己加 --api-level 24。
反过来的问题：用了 API 26 才有的接口，构建时发现不了，运行时才崩。工具链是 API 26，模拟器是 API 24。在一个按 --api-level 24 新建的工程里调用 fs.listFileExtSync（@ohos.file.fs 里 API 26 才有的函数），实测：
命令行构建成功，只给一条“函数可能抛异常”的通用提醒；ArkTS 检查同样只有这条通用提醒；Lint 报 0 问题（Lint 确实在运行，埋一个未使用的变量能被报出来）。也就是说构建阶段没有任何一步比对接口的版本。
装到模拟器上（系统 6.1.0.126，API 24）直接调用：应用一启动就崩，崩溃报告是 TypeError: listFileExtSync is not callable，位置就是调用那一行。用 try/catch 包住则能接住，应用照常运行。
对现有迁移结果的影响：没有发现。只读扫描了同事流水线的 155 个任务，其中 87 个有完整工程（全部声明的是 6.1.1(24)），共 6795 个源文件，对照 SDK 里 API 26 新增的接口（704 个模块级名字、38 个全新模块、1214 个只在 API 26 出现的方法 / 属性名），按每个文件的 import 关系比对，结果是 0 处。这个扫描器在探针工程上能扫出埋下的调用，在干净的模板工程上是 0。
这个风险没法靠换版本消除（没有 API 26 的模拟器系统镜像），只能加防护：把扫描加成流水线里的一步，或者给 agent 写一条“只用 API 24 及以前的接口”的规则。这两样都还没做。

check compat 不可用 是另一件较小的事：该功能要求命令行工具 ≥ 26.0.1，只影响这一个命令。升级命令行工具会同时换掉 SDK 和模拟器程序，可能影响与现有 API 24 系统镜像的兼容性，以及同事流水线已验证过的构建行为，所以没有动。

五、镜像里做的非默认设置

项内容原因
编译期开关 --skip-agreement产品协议的硬性检查直接放行上游构建脚本自带的开关，注释写明用于源码/内部构建，发布版固定关闭。本镜像仅内部使用，所以开启（用户确认）。实测删掉协议接受文件后 agent 对话照常进行
协议接受模拟器许可；另保留产品协议的接受记录许可必须接受。产品协议的硬性检查已被上面的开关绕过，保留接受记录只是因为交互式界面的引导流程只看本地记录、不看那个开关
隐私关闭数据统计、工具改进计划、CLI 遥测、自动更新检查默认都开启；服务器上批量跑不向华为上报使用数据
窗口模式入口脚本自动拉起 Xvfb :0，DISPLAY=:0无窗口模式模拟器无法注册到 hdc；截图对比和 VNC 也要窗口模式
预置模拟器实例deveco_phone，已完成首次启动（0.76GB）新容器首次启动 30 秒，而不是 85 秒加一条超时提示
Lint 默认生效给 devecocli create 的配置模板加一条规则（enable-lint.py）上游的默认配置会被检查器跳过，新建工程的 Lint 什么都不查却显示“无问题”。见第十一节

镜像设置了 ENTRYPOINT（先启动虚拟显示器再执行原命令），不想要时用 docker run --entrypoint bash ...。

宿主机侧另外核对了四件事：

  • 构建可复现：同源码同脚本再构建一次，二进制 sha256 逐字节一致。
  • 交付文件一致：本地的 Dockerfile、入口脚本、构建脚本、补丁、自检脚本等 7 个文件与服务器上的副本逐字节相同。
  • HMBot 无回归：最终镜像上 rsi 的引擎自检（本地 + 带模型）均通过。
  • 启动方式：默认进 bash、带命令启动（rsi 的用法）、--entrypoint bash 绕过入口，三种都正常。

按文档重建验证（2026-11-24）：按 README“怎么重建”的步骤，只用仓库里的文件在服务器上重建了一遍镜像（第 1 步沿用已有的构建产物），再在全新容器里跑自检：44 通过，0 失败，1 跳过（未提供模型令牌，agent 部分整组跳过）。预置的模拟器实例在新容器里冷启动 40 秒。过程中发现并修掉了预置脚本 prepare.sh 的一个问题：它导出的目录多了一层 .Huawei/，照它重建出的镜像里找不到实例；修正后加了导出布局的断言。重建得到的实例约 0.8GB，比当前镜像里的大 60MB 左右（缓存分区文件），不影响使用。这一次自检用的脚本还没加强安卓截图、界面验证、agent 安装启动三项的判定（见第十二节）。日志见 deveco-code/evidence/selfcheck-rebuild-20261124.log。

自检中确认的两个使用细节：
  • 鸿蒙和安卓模拟器同在一个容器时，鸿蒙先占 5555 端口，安卓会顺延到 5556/5557，在 adb 里显示为 emulator-5556 而不是 emulator-5554。写死设备名的脚本要动态取。
  • 镜像带了入口脚本，docker run 镜像 -c "..." 不会自动补 bash，要显式写 bash -c。

十一、几项“不可用 / 不检查”的具体含义

这几项之前只有一句结论，这一节说明它们各是什么、在 Linux 上实际的表现、对使用有什么影响，以及依据。前三项不影响已经验证通过的构建、运行、模拟器、界面验证等核心流程。（2026-11-24 更正：“语言服务”一项原先写的是“不可用”且原因标了“未确认”，读源码并实测后已改正，见下表。）

功能它是什么在这个镜像里的实际表现影响与依据
语言服务编辑器背后的代码理解能力：不构建就报出编译错误、按名字搜符号、看文件里有哪些函数、代码格式化是 DevEco Code 自带的功能，不是要对接的外部服务（不用配地址、令牌），但默认关闭。启动日志写着 all LSPs are disabled 和 all formatters are disabled。在 deveco.json 里写 "lsp": true 后，日志变成 enabled LSP servers …：给一个引用了未定义变量的 .ts 文件要诊断，能即时报出 Cannot find name 'undefinedVariable'；给同样有错误的 .ets 文件要诊断，仍返回空的 {}影响：对鸿蒙工程没有变化——ArkTS 代码没有即时的诊断和格式化，agent 要知道代码有没有编译错误只能靠构建和 devecocli check arkts。实测 agent 就是这么做的（每次都先构建），所以不阻塞。
它怎么工作：DevEco Code 自带“提问”的那一半；“回答”的那一半是每种语言一个的程序，第一次用到时 DevEco Code 自己从 npm 下载到缓存目录（实测约 9MB），可以用 DEVECO_DISABLE_LSP_DOWNLOAD 关掉下载，也可以在配置里指定自己装的。
依据：源码 lsp/lsp.ts 里，只有配置的 lsp 一项为空或 false 时才打印 all LSPs are disabled；配置项的说明是“不写或设为 false 即关闭，true 启用内置的，或写成对象启用内置的并加覆盖”。所以各个平台默认都是关闭，不是 Linux 特有的。内置的 38 种语言服务器（v1/config/lsp.ts 的 builtinServerIds）里没有 ArkTS；内置命令行工具里 assertLsp() 直接转给 assertStudio()，即 ArkTS 的语言服务随 DevEco Studio 提供，Studio 没有 Linux 版，所以这部分在 Linux 上补不上。
打开时的一个坑：工程里的 typescript 包要是 5.x。直接 npm install typescript 现在装到的 7.0.2 里没有它要找的 lib/tsserver.js。
未确认：官方安装包会不会自带一份打开语言服务的配置（没有官方的 Linux 安装包，无法对比）
命令沙箱限制 agent 执行的命令能做什么：read-only（只读）、workspace-write（只能写工作区）、full-access（不限）三档，由系统层强制执行不生效。所有命令都是直接执行，相当于永远是 full-access影响：如果想靠“只读”或“只能写工作区”来约束 agent，在这套镜像上不起作用，剩下的约束只有工具层的权限审批和容器本身的边界。用 --auto 无人值守时等于没有这层约束，所以容器就是唯一的安全边界。
依据：源码 tool/shell.ts 里 isSandboxPlatform = isMac || isWindows；依赖的 @bitfun-ai/sandbox 0.3.1 在 npm 上只有 Windows 和 macOS 平台包
check compatSDK 兼容性扫描：检查源码用了哪些在目标 SDK 版本里变更或废弃的接口，需要指定源版本和目标版本，可导出报告报错 The apicompat component is missing. The detected Command Line Tools version is 26.0.0.821. The minimum required version is 26.0.1影响：只影响这一个命令。agent 做跨 SDK 版本升级时没有这个辅助工具。
依据：实测报错原文
check lint代码规范检查：按 code-linter.json5 里的规则查问题，模板默认启用了性能规则、TypeScript 推荐规则和一组安全规则镜像里新建的工程默认生效。上游原版在这里什么都不检查：结果是“检查了 0 个文件、无问题”上游的问题：新建工程自带的配置与检查器内置的默认配置完全相同，命令行模式下检查器遇到默认配置会跳过执行规则的引擎，连模板里写成 error 的安全规则也不执行，等于给了一个假的“全部通过”。
依据：检查器日志 Using default configuration, skipping ESLint engine（整个过程 0.05 秒）。对照实验：默认内容 + 默认文件名 → 跳过；默认内容 + 其他文件名 → 跳过；非默认内容 → 报出了未使用变量。所以是按内容判定是否为默认配置
镜像里的处理：enable-lint.py 给 devecocli create 的配置模板加一条 @typescript-eslint/no-unused-vars（本来就在推荐规则集里，显式写出只为让配置不等于默认）。参数设成不检查未使用的函数参数，因为模板自己的 EntryAbility.ets 就有两个未使用的回调参数，否则每个新工程一建出来就带两个“错误”。实测：干净的模板工程 0 问题；埋入未使用的导入和局部变量后被报出；命令行直接用的 devecocli 和 DevEco Code 内置的那一份都生效
仍然要注意：只对镜像里新建的工程生效，已有工程若配置还是上游默认内容需要自己改；汇总里的 Files checked 统计的是有问题的文件数，引擎被跳过和检查过没问题都显示 0，不能据此判断 Lint 是否真的跑了；同一个文件里的 any 类型和 MD5 调用即使把对应规则设成 error 也没被报出，原因不明；这是否只在 Linux 命令行模式下如此没有确认

值得反馈给 DevEco Code 团队的

  • 新建工程自带的 Lint 配置刚好触发“默认配置跳过”，默认情况下规则全部不执行。
  • 模板生成的 EntryAbility.ets 违反模板自己的 Lint 规则。
  • 鸿蒙能力不在二进制里：缺少运行时依赖时没有任何提示，只是静默地没有功能。
  • 新模拟器实例首次启动的时间超过 CLI 的等待时间；冒烟检查的等待时间在冷启动下不够。
  • 官方实机用例有 4 个只适配了 Windows。
  • 命令行构建不比对接口版本：工程声明的兼容版本低于所用接口的版本时，构建、ArkTS 检查、Lint 都没有任何提示，运行时才崩。
